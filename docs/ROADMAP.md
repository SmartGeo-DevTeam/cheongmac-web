# CHEONGMAC 개발 로드맵

> 기준일: 2026-11-10. 사용자가 확정한 개발 순서이며, 진행하면서 수정 가능하다.

## 진행 순서 (사용자 확정)

1. **완료 — Architecture v1 및 페이지 조립 구조 정리**
   - `_components`/`_ui`/`_data`/`_types`/`_lib`/`_assets`/`_providers`, `(site)`/`(api)` 기준 확정.
   - 기존 페이지 UI/스타일을 유지한 1차 구조 정리.
2. **진행 — 신규 진료 메뉴와 빈 페이지 골격 구성**
   - 혈관중점진료 5개 2차 메뉴 + 18개 3차 메뉴, 종합진료 6개 2차 + 22개 3차 메뉴.
   - 상위 진입 2개까지 총 53개 라우트 골격. UI 본문은 비워 둠.
   - `isPublished: boolean`으로 메뉴별 공개 여부 지정. 기본 `false`, 미공개 직접 접근은 `notFound()`.
3. **우선 — 프론트엔드 페이지를 하나씩 구현**
   - 2·3차 메뉴별 콘텐츠·디자인·SEO·반응형 개발.
   - 완료된 페이지부터 상위 메뉴 및 해당 항목의 `isPublished`를 `true`로 변경.
   - 기존 정적 데이터는 `_data`로 유지. 새 페이지도 Architecture v1 규칙 적용.
4. **그다음 — Supabase DB 설계 및 연결**
   - UI가 어느 정도 완성된 뒤 DB 스키마·마이그레이션·권한(RLS)·서버 repository를 구축.
   - `_data`의 콘텐츠를 도메인별로 전환하되 UI Props 계약을 최대한 유지.
5. **이어서 — Azure 에셋 이전 및 관리**
   - 이미지·첨부파일의 공개/비공개 저장 정책, URL·메타데이터, 업로드·삭제 기능 구축.
   - 기존 `public/` URL은 일괄 변경하기 전에 이관·호환 방식을 검증.
6. **그다음 — 관리자 페이지 구축·연동**
   - Supabase Auth·관리자 권한과 콘텐츠 CRUD, Azure 미디어 관리 기능.
   - 실제 운영용 검수·게시·이력 관리.
7. **최종 — 통합 검증·운영 배포**
   - 타입·빌드·라우트·비공개 접근·검색·SEO·모바일·성능·보안·백업 점검.

## 작업 원칙

- 사용자 요청에 따라 **추가 페이지 UI를 먼저 개발하고**, DB/Azure/CMS의 본격 연동은 뒤로 미룬다.
- 다만 DB로 전환할 데이터 속성과 공개/비공개 요구사항은 UI 작업 중 기록해 재작업을 줄인다.
- 비공개 `isPublished` 플래그는 **콘텐츠 발행용 기능 플래그**이지 로그인/민감정보 접근 제어 수단이 아니다.
- 완료 단계·일정·명명 규칙이 바뀌면 이 파일을 업데이트하고 `docs/ARCHITECTURE.md`의 결정 기록에 사유를 남긴다.
- 기존 코드나 스타일은 현재 요청만으로 재설계하지 않는다.
